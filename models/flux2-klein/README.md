# FLUX.2 [klein] 4B for WebGPU: Thomas the Jank Engine

Generate images from a text prompt with [FLUX.2 [klein] 4B](https://huggingface.co/black-forest-labs/FLUX.2-klein-4B) running entirely in the browser. The text encoder, the diffusion transformer and the image decoder all run on the visitor's GPU through WebGPU, using the [Kaminos inference kit](../../webgpu-inference-kit/README.md). No server does any of the work.

**[Ride Thomas the Jank Engine in your browser](https://lyonsno.github.io/kaminos/inference-kit/klein/)**

## What it does

- **The whole model in the browser.** The Qwen3-4B text encoder (the 27 layers whose hidden states the model reads), the 4-step rectified-flow transformer and the VAE decoder all run as WGSL compute shaders.
- **A 3.2 GB download, cached.** Weights are int4 (groups of 128, weight-only), packed per block, downloaded as gzip copies that the page inflates, and kept in the browser's Cache API after the first visit. The 0.8 GB token-embedding table is never downloaded whole: the page fetches only the rows a prompt uses, with HTTP range requests.
- **Pick your jank level.** Mint is the int4 model (3.2 GB). Weathered uses a 3-bit transformer and looks about the same (3.0 GB). Off the Rails uses a 2-bit transformer: blurry, melted and still recognizable (2.5 GB). The levels share the text encoder and image decoder, so switching after the first download fetches only the other transformer.
- **Watch it form.** After each of the four steps the page shows a rough preview: the model's current estimate of the finished image, mapped to colour by a small linear fit of the VAE decoder ([`fit-latent-preview.py`](fit-latent-preview.py)) and drawn at an eighth of the output size. On the M2 Pro the first preview appears about 3 seconds into a 13-second image. The preview machinery is the inference kit's `createWebGpuLatentPreview`, usable by other latent models.
- **Room for the application to keep rendering.** Model work is submitted as inference-kit command duties sized to measured GPU throughput, so a renderer on the same device keeps its frame rate during generation. Generation can be paused, resumed and stopped between duties.
- **Same output either way.** A generation that shares the GPU produces the same pixels as one that runs without yielding, and on a given machine and browser the same seed and prompt reproduce the same image.

## Speed

Times are for one image with 4 steps (the page's Full button) in Chrome, sharing the GPU with a continuously rendering scene.

| Size | 16 GB Apple M2 Pro | Apple M4 Max |
| --- | --- | --- |
| 512 × 512 | about 13 s (about 5 s more with better lettering) | 6–7 s |
| 768 × 768 | 40–46 s | about 12 s |
| 1024 × 1024 | about 57 s | about 23 s |

During generation the scene kept a median frame time of about 20 ms on the M2 Pro.

The page has four generate buttons that trade steps for time. The model is distilled for 4 steps, but 3 look nearly the same, 2 are smoother and simpler, and 1 gives a blurry, melted impression of the scene. At 512 × 512 on the M2 Pro:

| Button | Steps | Time |
| --- | --- | --- |
| Full | 4 | about 13 s |
| Fast (the default) | 3 | about 10 s |
| Express | 2 | about 7.5 s |
| JANK | 1 | about 4.5 s |

Prompts are padded with filler tokens before the transformer reads them. The page pads to the prompt's own length plus a few tokens, which is about a quarter faster than the reference pipeline's 512, unless the prompt asks for lettering (quoted text, words in capitals, or words like sign, poster or title). Then it pads to 512, which spells words in the image noticeably better. A checkbox shows which mode will run and can be flipped. Generating again with the same prompt reuses its text encoding.

## Memory

The weights take 3.6 GB of GPU memory. Working memory grows with image size, so the transformer's buffers are released before the image decoder allocates its own, and the decoder's are released once the image is read back. The decoder stores its activations in 16 bits, and attention in both the transformer and the decoder keeps at most 64 MiB of scores at a time (a few heads, or a block of query rows).

**Low-memory mode** (a checkbox on the page, ticked by default on phones and devices reporting less than 8 GB) never holds the text encoder and the transformer at the same time. A new prompt reloads the text encoder from the browser cache in place of the transformer, encodes, and swaps back; generating again with the same prompt swaps nothing. Images are identical in both modes.

Peak GPU memory measured by the page on the 16 GB M2 Pro:

| Size | Normal | Low-memory mode |
| --- | --- | --- |
| 512 × 512 | 4.2 GB | 2.8 GB (a new prompt takes about 2 s longer) |
| 1024 × 1024 | 5.8 GB | 4.3 GB |

With about 6 GB of memory left to the browser and macOS (the rest held by a test process), low-memory mode ran without the system swapping, while normal mode pushed it to swap about 3 GB. Neither figure comes from a real 8 GB Mac or a phone yet.

**Phone-class GPUs.** Many phones allow at most 128 MiB per storage buffer binding, the WebGPU default. The page reads the device's limits: sizes whose buffers would not fit (768 and up at that limit) cannot be picked, and better lettering pads the prompt only as far as the limit allows (189 tokens at 512 × 512 instead of 512). Generation at 512 × 512 passes with Chrome holding the GPU to the default limits; add `?limits=baseline` to `generate.html` to try it.

## Running it

The [demo page](index.html) loads weights from [BasinShapers/flux2-klein-4b-webgpu](https://huggingface.co/BasinShapers/flux2-klein-4b-webgpu). Add `?weights=<base URL>` to load them from elsewhere; the base must contain the `te/`, `dit/` and `vae/` folders.

To pack the weights yourself from the original checkpoint:

```sh
hf download black-forest-labs/FLUX.2-klein-4B
python pack-text-encoder.py --model-dir <snapshot> --format i4 --out weights/te
python pack-transformer.py --model-dir <snapshot> --format i4 --globals-format i8 --out weights/dit
python pack-vae.py --model-dir <snapshot> --out weights/vae
node serve-klein.mjs --te weights/te --dit weights/dit --vae weights/vae
```

Then open `http://localhost:18709/index.html?weights=` (an empty base loads from the local server). The packers need Python with `torch`, `safetensors` and `numpy`.

## Using it in an application

Use `createKleinApp()` to load the model, generate an image and draw it to a canvas. Keep the app for more prompts, then release it when you’re finished. It creates its own WebGPU device and schedules generation cooperatively.

The application interface is in this checkout. Its npm release, `@kaminos/flux2-klein@0.1.2`, is pending; the currently published `0.1.1` has only the direct pipeline interface. Until the new version is published, build the application package from source. From the Kaminos repository root:

```sh
node models/flux2-klein/pack-klein.mjs --out /absolute/path/to/klein-package --version 0.1.2
```

In your own application directory, install the resulting tarball. This installs the published inference kit as its dependency:

```sh
npm install /absolute/path/to/klein-package/kaminos-flux2-klein-0.1.2.tgz
```

Save the following as `index.html` beside your application's `node_modules`, serve that directory with `python3 -m http.server 8080`, and visit `http://localhost:8080`. Chrome with WebGPU and `shader-f16` is required. The first generation downloads about 3.2 GB of hosted Mint weights, cached for later visits; see [memory requirements](#memory) above.

```html
<!doctype html>
<html lang="en">
<meta charset="utf-8">
<meta name="viewport" content="width=device-width, initial-scale=1">
<title>My first Klein image</title>
<script type="importmap">
{ "imports": {
  "@kaminos/flux2-klein": "./node_modules/@kaminos/flux2-klein/index.js",
  "@kaminos/webgpu-inference-kit/core": "./node_modules/@kaminos/webgpu-inference-kit/src/core.js"
} }
</script>
<form id="prompt-form">
  <label>Prompt <input id="prompt" required value="a blue tank engine on a sunny branch line"></label>
  <button id="generate">Generate</button>
  <button id="release" type="button" disabled>Release model</button>
</form>
<p id="status" role="status">Enter a prompt and generate an image.</p>
<canvas id="image" aria-label="Generated image" style="max-width:100%;height:auto" hidden></canvas>
<script type="module">
import { createKleinApp } from '@kaminos/flux2-klein';

const form = document.getElementById('prompt-form');
const prompt = document.getElementById('prompt');
const generate = document.getElementById('generate');
const release = document.getElementById('release');
const status = document.getElementById('status');
const canvas = document.getElementById('image');
let klein;

form.onsubmit = async event => {
  event.preventDefault();
  generate.disabled = release.disabled = true;
  try {
    if (!klein) {
      status.textContent = 'Loading model weights…';
      klein = await createKleinApp({
        onProgress: (part, file, { loadedBytes, totalBytes }) => {
          status.textContent = `Loading ${part}: ${Math.round(100 * loadedBytes / totalBytes)}%`;
        },
      });
    }
    status.textContent = 'Generating…';
    const image = await klein.generate({
      prompt: prompt.value, seed: 7, width: 512, height: 512, steps: 3,
      onPhase: phase => { status.textContent = `Generating: ${phase}…`; },
      onStep: (step, steps) => { status.textContent = `Step ${step} of ${steps}…`; },
    });
    canvas.width = image.width;
    canvas.height = image.height;
    canvas.getContext('2d').putImageData(new ImageData(image.rgba, image.width, image.height), 0, 0);
    canvas.hidden = false;
    status.textContent = 'Done. Enter another prompt to reuse the loaded model.';
  } catch (error) {
    status.textContent = `Could not generate: ${error.message}`;
  } finally {
    generate.disabled = false;
    release.disabled = !klein;
  }
};

release.onclick = async () => {
  generate.disabled = release.disabled = true;
  try {
    await klein.destroy();
    status.textContent = 'Model released. Generate again to reload it from the cache.';
  } catch (error) {
    status.textContent = `Could not release: ${error.message}`;
  } finally {
    klein = undefined;
    generate.disabled = false;
  }
};
</script>
</html>
```

The [package API guide](package-README.md) covers progress, previews, weights, low-memory mode, pause/resume/stop and device ownership. `generate()` retains the model's options, callbacks and full output. `pipelineOptions` at creation forwards model settings such as `weightsBase`, `level` and `residency`.

### Sharing a device with your renderer

Pass `{ device }` to borrow an existing WebGPU device with `shader-f16`, or `{ session, foreground }` to use your host's inference session and foreground service. Destruction leaves borrowed resources open. With `load: false`, attach your renderer through `app.foreground` before `app.load()`, so the same attachment serves frames before, during and after generation. The package guide documents that callback contract.

[`examples/external-app`](examples/external-app) exercises that composition, including load failure, progress, generation previews, pause/resume, repeat use and borrowed-device survival. `node run-external-app.mjs --chrome <exe> --weights-dir <dir> --out <dir>` installs the example from packed tarballs outside this checkout and runs it.

### Direct pipeline control

`KleinPipeline` remains available when your host already owns its inference invocation and scheduling:

```js
import { KleinPipeline } from '@kaminos/flux2-klein';

const klein = new KleinPipeline(device);
await klein.load(onProgress);
const image = await klein.generate({ prompt, seed, width: 512, height: 512, steps: 3, onStep, onPreview });
await klein.destroy(); // frees Klein's buffers; the borrowed device stays yours
```

For that lower-level path, a `schedule` supplies the inference-kit route runtime and queued invocation. [`createKleinDemo`](klein-demo.js) shows the demo's complete wiring. The application interface manages that lifetime for ordinary use.

## Local reference-image edits in Kaminos

The Generate tab can use the selected image as a reference with FLUX.2 Klein 4B.
Pack the encoder alongside the existing local `te/`, `dit/` and `vae/` directories
with `python models/flux2-klein/pack-vae.py --model-dir <snapshot> --encoder --out <package>/encoder`,
then mount that package with `KAMINOS_KLEIN_WEIGHTS_ROOT`. Select an image, choose
FLUX.2, enable **Use selected image as reference**, and enter the edit prompt.
The saved image retains the reference digest and the image-and-text route.
The reference keeps its own aspect ratio, is reduced only above 1024² pixels,
and is cropped to the sixteen-pixel latent grid; output dimensions are chosen separately.

The pipeline accepts `reference: {rgb, width, height}` (row-major RGB floats in
[-1,1], dimensions divisible by sixteen) and an optional `encoderUrl`.
The encoder is loaded on the first reference request. Existing hosted packages
without `encoder/` still support text-to-image; reference requests fail visibly
if their encoder is unavailable. FLUX.2 reference tokens use T=10 with unscaled
row/column coordinates and remain fixed between denoising steps.

# Landing on main

Lanes land by fast-forwarding `main` to their branch tip; there are no pull requests. On 2026-10-13 main went red because a lane pushed a commit to `main` that had never had a green run of the `tests` workflow for that exact commit. `tools/land.mjs` makes that push conditional.

Main is protected by a required status check, `suite`, the job of the `tests` workflow. Only a run triggered by a push satisfies it: a `workflow_dispatch` run for the same commit, green or not, does not, and a push to main of a commit whose only run was dispatched is refused with GH006 "Required status check suite is expected". The tool therefore gets the run by pushing, never by dispatching. A commit whose only run was dispatched needs the tool run again: it pushes the `land/<sha>` ref and gets a push run.

## What it checks

The commit is read once, at the start; every step checks, triggers a run for and pushes that commit, not whatever HEAD is by then. In order; the first failure ends the run.

1. **clean-tree**: `git status --porcelain` is empty. Modified and untracked files both count.
2. **fetch**: `git fetch <remote> +refs/heads/main:refs/remotes/<remote>/main`.
3. **rebased**: `git merge-base <remote>/main <commit>` equals `<remote>/main`, so the branch contains current main and the push is a fast-forward. A commit main already contains is behind main; one that diverged must be rebased first. A rebase makes a new commit, which needs its own run.
4. **ci**: `gh run list -R <owner/name> --workflow tests.yml --commit <commit> --json ...`. Only a push run for the commit counts: a run whose head SHA is not the commit, or whose event is not `push` (a `workflow_dispatch` run, which the required check ignores), is listed in the receipt with `counted: false` and its reason, and is never awaited. The latest completed push run decides, and it must have concluded `success`. A failed run refuses; the message also reports main's own latest run with both run URLs ("main is also red at run N; compare the failures before attributing"), without deciding whose failure it is. A push run already queued or running is awaited. When no push run is listed, the tool first looks among the workflow's push runs created in the last ten minutes, listed without the `--commit` filter (which can lag), and awaits one for the commit instead of pushing again; a dispatched run never qualifies. It then reads the commit's own `.github/workflows/tests.yml` and refuses with `ci-no-trigger` when its push trigger does not include `land/**` (or the file is missing): pushing the ref would run nothing, and rebasing onto main brings the trigger in. Otherwise the tool force-pushes the commit to its own ref, `land/<sha>` (never the lane's branch and never main, so a checkout on `main` or a branch that diverged from its remote copy changes nothing it should not). That push is the trigger: `.github/workflows/tests.yml` runs on pushes to `land/**`. A `land/<sha>` ref already at the commit is deleted and pushed again, since pushing an unchanged ref fires nothing; one at another commit is replaced. The tool then lists runs for the commit until the push run appears and concludes. It never calls `gh workflow run`. A ref this run pushed is deleted when the attempt concludes, whatever the outcome, and the receipt records the deletion. A failed run is refused and the ref is not pushed again for it.
5. **push**: `git push <remote> <commit>:refs/heads/main`. An interruption during this push says so and reads main back: "interrupted during the push to main; main is now <commit>". If main moved between the check and the push, git rejects the non-fast-forward; that is reported as the outcome `main-moved` and not retried. Rebase onto the new main and land again once the rebased commit has its own green run. A push that exited 0 is landed whatever happens afterwards; main is read back for the receipt only.

## Waiting for a run

A run usually takes 10 to 15 minutes (the suite itself is about seven), and up to about 70 at the job timeout. Run the tool in the background, or run it again later: a re-run finds the pending push run and awaits it rather than pushing the ref again. While waiting, the tool polls every 30 seconds and prints one line to stderr per state change (pushed, queued, in progress, concluded). The wait is bounded per state by the workflow's own lifecycle: ten minutes for the push run to be listed at all after the `land/<sha>` push, GitHub's 24-hour queue limit, then the job's `timeout-minutes` from `.github/workflows/tests.yml` once it runs (a job without the key runs to GitHub's default of 360). SIGINT or SIGTERM, to the tool or to its whole process group (a `gh` or `git` killed mid-call by the same signal is recorded in the receipt's `error`), ends the wait with a partial receipt naming the run being awaited, exit code 130; the run itself continues on GitHub. Interrupted after the ref push but before gh listed the run, a re-run within ten minutes finds that run among the recent push runs; after that, check `gh run list` before running again, since a re-run would push again and start a second run. A run that was cancelled or failed on infrastructure is re-run by hand with `gh run rerun <run id>`; the tool then awaits attempt 2 of the same run, and it never pushes the ref again on its own. By hand: `gh run watch <run id>`.

## Running it

```sh
node tools/land.mjs --dry-run    # every check against existing runs; changes nothing on the remote
node tools/land.mjs --ci-only    # get this commit's run green through land/<sha>, report, never push main
node tools/land.mjs              # land: push land/<sha> and wait if needed, then fast-forward main
```

Flags: `--dry-run` (implies `--no-dispatch`: no ref is pushed, so nothing runs); `--ci-only`; `--no-dispatch`, or its alias `--no-trigger` (refuse instead of pushing the `land/<sha>` ref, and say how to get a run); `--receipt <path>` (default `test-results/landing-<commit>-<time>.json` under the repository, a path git ignores); `--remote <name>` (default `origin`); `--repo <owner/name>` (default: from the remote's push URL); `--root <path>`; `--gh <path>` and `--git <path>` to substitute the executables. `--dry-run` and `--ci-only` exclude each other. Exit 0 when landed, or when a dry run or `--ci-only` passed every check; 1 when refused, including `main-moved`; 2 on bad arguments; 3 when the run could not find out: a fetch, gh query, `land/<sha>` push or main push that failed, a wait that outlived the workflow's lifecycle, or a receipt that could not be written; 130 when interrupted. It prints one summary line naming the outcome and the receipt.

## The receipt

JSON with schema `kaminos.landing-receipt.v2` (v2 replaced v1's `ci.dispatch` with `ci.trigger`):

- `outcome`: `landed`, `dry-run`, `ci-only`, `refused`, `main-moved`, `error` or `interrupted`, with `ok`, `reason`, the one-line `message` and, for an error, its `failurePhase`; for an interruption that also killed a child mid-call, that child's failure in `error`.
- `sha`, `branch` (null when detached), `remote` (name, push URL, the resolved repository and whether it came from the URL or `--repo`), and the mode flags.
- `main.before`, as fetched; `main.after`, as the remote reports it after the push stage, null when the run ended before it or main could not be read back (then `afterError` says why); `afterContainsSha`.
- `ci`: the workflow file, the first `gh` command and how many queries were made, the `--limit` and whether a listing filled it, every run returned (id, status, conclusion, workflow, head SHA, event, branch, URL, creation time, attempt, whether it counted and, when not, why: another commit, or not a push run), the run the decision rested on, main's own latest run when the decision was a failure, the recent push run awaited instead of pushing when one was found (`recentRun`), the trigger (the `land/<sha>` ref, whether it was already at the commit and so deleted and pushed again, the commit it held otherwise, whether it was pushed and when, whether it was deleted) and the wait (polls, elapsed time, every state change with its time, and the bounds with where the job timeout came from).
- `checks`: every check with `pass`, `fail` or `skipped` and its detail.
- `push`: exit code and both streams, or null when no push was attempted.
- `startedAt`, `finishedAt`, and the effective `git`, `gh` and poll interval.

The receipt is written whenever it can be, for a landing, a refusal, an error or an interruption alike; if writing it fails, the summary still prints, the error goes to stderr, and the exit code is 3. `tests/land-contracts.mjs` runs the tool against a bare origin, a clone and the stub `gh` in `tests/land-gh-stub.mjs`, on a clock the contracts control.

# Material recipes

Select a mesh and open **Material** beside Selection and Scene. Choose its surface slot, then create a named material or assign an existing one. The users readout identifies the edit scope. **Make unique** copies the recipe for the selected slot. The native Undo/Redo and scene Save/Open carry names, parameters and assignments.

A recipe configures a complete code-authored implementation. `scene-material-recipes.mjs` owns JSON identity, validation and slot bindings. `scene-material-programs.mjs` supplies complete rendering programs. Each program receives the slot's source material and accepted parameters and returns `{material, update(parameters), dispose()}`. Its code can construct an arbitrary node material; its `fields` describe the controls intentionally exposed in the common inspector. `check` may supply implementation-specific parameter validation. Register the pure descriptor alongside the runtime implementation so document preflight can reject unsupported implementations or versions before replacing the current scene.

The initial implementations are **Asset surface**, which preserves each slot's original maps and shading while overriding its finish; **Standard surface**, which supplies an independent standard finish; and **Kiln glaze**, a complete procedural ceramic program with fired color variation, glaze coverage, roughness, micro relief and clear coat. Changing the glaze parameters updates uniforms without rebuilding the program. These are complete implementations, not nodes in an imposed universal graph.

Recipes have stable IDs and implementation versions. Scene version 12 stores `materialLibrary: {recipes, bindings}`. Bindings identify an authored object and a source hierarchy/material-array slot. Missing recipes, unsupported implementations/versions, duplicate bindings and absent object references fail scene preflight. A changed source hierarchy that no longer contains a saved slot fails application rather than assigning another slot. File-backed objects reload their original source and then receive the recipe; textures are not duplicated into the document. Old scenes without the library retain their source appearance.

Runtime instances and source textures are derived resources. Each assigned slot owns its program instance, allowing source-specific maps and later object state to stay independent while sharing authored values. Parameter edits update existing instances; replacement/unassignment retires only the derived material. Duplicate shares the recipe and clones the original source, not the derived program. The library retains unassigned named recipes during the scene session and saves them explicitly.

Live burning currently owns its surface adaptation. The inspector identifies that owner and holds base-material authoring while Burning is enabled; this slice does not move heat, char or damage into shared recipe parameters. Annular burner field controls and other specialized existing material owners remain with their domains. This first context follows selection; pinning, texture replacement tools and broader owner-specific controls remain follow-up work.

`node --test tests/scene-material-recipes.mjs` covers persistence, validation, material arrays, sharing, uniqueness through native history, source texture preservation, program reuse and resource retirement. `demos/material-recipes/two-finishes.glb` is a 3,828-byte fixture exported with the installed Three GLTFExporter: one box with alternating textured woven panels and brass ends. Its six imported primitives exercise distinct source slots through the actual GLTF loader.
